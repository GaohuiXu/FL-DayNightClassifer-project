## 2. Code Risks

### R-001 — Active YAMLs leave `partition-seed` unset; seed variance is confounded with partition variance. **HIGH**

**Location**: `fl_v2/configs/experiments/cycle_02/phaseD2/*.yaml` (20+ files); fallback logic at `fl_v2/src/fl_v2/client_app.py:61-63`; default at `fl_v2/pyproject.toml:96`.

**Defect**: `_resolve_partition_seed` (`client_app.py:53-64`) reads `partition-seed` if set, else falls back to `seed`. The pyproject default for `partition-seed` is the empty string. **None of the 20+ active phaseD2 YAMLs override it.** Therefore every "seed=42 vs seed=43" comparison in the active codebase is also a "partition A vs partition B" comparison. The infrastructure to fix this is in place — there's even an example at `_partition_seed_decoupling_example.yaml` — but it's not used in practice.

**Evidence**:
- `grep -n 'partition-seed' fl_v2/configs/experiments/cycle_02/phaseD2/*.yaml` returns hits only inside `_partition_seed_decoupling_example.yaml` (an example file). All other YAMLs in the active tree set only `seed: 42`.
- `fl_v2/pyproject.toml:96`: `partition-seed = ""`.
- `client_app.py:62-63`: `if isinstance(raw, str) and raw.strip() == "": return int(run_config["seed"])`.

**Fix proposal**:
1. Change the pyproject default to a constant (e.g., `partition-seed = "0"`) so unset YAMLs all share one partition.
2. **OR** add a runtime warning in `_resolve_partition_seed` when the fallback fires, so users know they're conflating axes.
3. Update active phaseD2 YAMLs (the runA/runB pairs and `_phase3_fixed_*` set) to set `partition-seed: 0` explicitly.
4. **For the upcoming Cycle 02 rewrite**: drop the empty-string fallback entirely. `partition-seed` should be a required field or default to a constant; never derive from `seed`.

**Bit-determinism risk**: **yes** — changing the default re-partitions every existing experiment. Any cached `summary.json` / wandb run with `partition-seed=""` will not bit-match a re-run with `partition-seed=0` if the previous run had `seed != 0`. Action plan: keep the default change scoped to YAMLs we're about to re-run; don't change the pyproject default until the rewrite.

**Verification plan**: After fix, run two paired SLURM jobs with `seed=42` and `seed=43` but same `partition-seed=0`. Confirm via `client_label_histograms.json` that all 50 clients have identical per-class counts across the two seeds. Then confirm the per-seed `summary.json` shows non-trivial accuracy variance (otherwise the partitions are dominating noise).

### R-002 — Robust aggregators don't reject NaN inputs. **HIGH**

**Location**: `fl_v2/src/fl_v2/strategy/fed_median.py:62-64`; `fl_v2/src/fl_v2/strategy/fed_trimmed_avg.py:90-92`; `fl_v2/src/fl_v2/strategy/bulyan.py:115-123`; `fl_v2/src/fl_v2/strategy/norm_clipped_fedavg.py` (clipping helper).

**Defect**: All four custom robust aggregators stack client tensors with `np.stack(...)` and then call `np.median`, `_trim_mean`, or coordinate-wise selection. **None check for NaN.** If a malicious client sends a NaN-tensor (trivially producible from `torch.tensor(float('nan'))`), the aggregator:
- `np.median` along axis=0 returns NaN for any coordinate that has at least one NaN — propagates instantly.
- `np.partition` (used by `_trim_mean` at `fed_trimmed_avg.py:35`) treats NaN as larger than all real values, so for `cut_fraction=0.2` a single NaN client only gets trimmed if there are >5 clients. Below that, NaN passes through.
- Bulyan's `_aggregate_n_closest_weights` uses `np.argpartition` on `np.abs(layer_stack - ref_layer)` — `abs(nan) == nan`, and argpartition sorts NaN to the end, so the "closest" selection silently includes a NaN-distance client.
- norm-clipping's `compute_update_norms` is `np.sqrt(np.sum(x*x))` — produces NaN, the clip threshold check `min(1.0, clip_norm / (norm + 1e-12))` returns NaN → propagates.

For a USENIX-SEC 2026 defense study this is a *positive* finding to report (a real defense gap), but in our experimental code it means a numerically unstable honest client (rare, but possible with high learning rate × full_ft) can also poison aggregation.

**Evidence**: Manual code read of each aggregator. No `np.isnan` / `torch.isnan` anywhere under `fl_v2/src/fl_v2/strategy/`.

**Fix proposal**:
1. Add a `_drop_nan_replies` helper in `norm_tracking_fedavg.py` that filters `valid_replies` whose state_dict contains any NaN before aggregation. Log the dropped node_ids for auditability.
2. Call from every aggregator (including FedAvg's `super().aggregate_train`).
3. Decide policy: drop the reply silently, drop and warn, or drop and replace with the global model. For the USENIX-SEC story, **drop-and-warn** is the right default — it makes the defense look strict.

**Bit-determinism risk**: **no** — adding a NaN filter is deterministic per-input. Won't change behavior on existing (non-NaN) runs.

**Verification plan**: Add a test client that emits NaN in one parameter; submit the existing paired-SLURM verification suite; confirm (a) the malicious client's `partition-id` appears in a new "dropped_replies" log entry, and (b) the aggregated weights are identical to a run where that client's reply was synthetic-zero. Two new unit tests in `fl_v2/tests/test_strategy_nan_robust.py`.

### R-004 — FedMedian / FedTrimmedAvg / NormClippedFedAvg don't enforce a minimum honest-client quorum. **MED**

**Location**: `fl_v2/src/fl_v2/strategy/fed_median.py:34-36`; `fed_trimmed_avg.py:65-67`; `norm_clipped_fedavg.py:29-31`.

**Defect**: Each strategy's first check is `if not valid_replies: return None, None`. **That's it.** Even with a single reply, FedMedian computes a 1-element median (the client's own values), FedTrimmedAvg might raise (see R-010 below), NormClippedFedAvg clips and returns. Only Bulyan correctly enforces `n >= 4f+3` (`bulyan.py:80-90`).

For Krum/MultiKrum the wrapper (`krum_wrappers.py`) delegates to Flower's built-in, which we **trust** to enforce `n >= 2f+2` but I did not re-verify.

This matters because a successful defense under heavy attack should *refuse to aggregate*, not produce a low-confidence result that masquerades as a defended round. For USENIX-SEC, the contract should be: defense returns `(None, None)` if honest quorum can't be guaranteed; the server then carries the previous round's global model forward.

**Evidence**: Manual read of each `aggregate_train`. Only `bulyan.py:80-90` has a quorum check.

**Fix proposal**:
1. Add a `_check_quorum(self, valid_replies)` method on `NormTrackingFedAvg` that subclasses override.
2. For FedMedian: `n >= 2f+1` (median tolerates `f < n/2`).
3. For FedTrimmedAvg: `n > 2 * cut_fraction * n + 1` rearranged → `n >= ceil(1 / (1 - 2*beta))` for the trim to leave at least one element.
4. For NormClippedFedAvg: `n >= 1` is fine for the math, but a configurable `min_clients` parameter would be honest.
5. For Krum: explicitly assert `n >= 2*self.num_malicious_nodes + 2`.
6. **Verify Flower's built-in Krum** also enforces this (or document that we trust it).

**Bit-determinism risk**: **no** — new return-None paths only fire at edge cases that previously produced low-confidence aggregates. Won't affect production runs (50 clients, fraction-train ≥ 0.5 → always plenty of replies).

**Verification plan**: Unit tests in `fl_v2/tests/test_strategy_quorum.py` that submit `[5, 4, 3, 2, 1]` replies under varying `num_malicious_nodes` and assert correct `(None, None)` returns.

### R-006 — Wandb glue silently swallows 11 exception classes. **MED**

**Location**: `fl_v2/src/fl_v2/utils/wandb_logger.py:146, 155, 204, 237, 249, 257, 265`; `fl_v2/src/fl_v2/utils/wandb_artifacts.py:38, 47, 58, 77`.

**Defect**: Every wandb call site is wrapped in `try: ... except Exception:`. The catch typically logs to stdout and continues. 3. Add a once-per-run summary `[wandb] N exceptions swallowed: {kind1: count, kind2: count}` so we know if degradation happened.

**Bit-determinism risk**: **no** — wandb is fire-and-forget; doesn't affect numerical outputs.

**Verification plan**: Temporarily kill wandb auth on a smoke-test job; confirm the job still completes successfully and the new summary line appears in the SLURM log.

### R-007 — Cached model + load_state_dict doesn't reset `.train()` / `.eval()` mode. **MED**

**Location**: `fl_v2/src/fl_v2/client_app.py:198-210`; `fl_v2/src/fl_v2/training/train.py::train_local`; `fl_v2/src/fl_v2/training/eval.py::evaluate`.

**Defect**: `_load_model_from_message` reuses a cached `nn.Module` per Ray actor (correct optimization, doc'd at `client_app.py:182-189`), and `load_state_dict` overwrites weights AND buffers. **But it doesn't set `.train()` / `.eval()` mode.** The mode is whatever the previous call (the cached model's last user) left it in.

If `train_local` calls `model.train()` somewhere (it should) and `evaluate` calls `model.eval()` (it should), this is fine. If either omits, BatchNorm uses running stats vs batch stats inconsistently, leading to:
- val_accuracy reported during train_local could be biased (BN in train mode during eval pass).
- inter-round drift in BN running_mean/var because eval-mode forward passes (which freeze BN updates) might happen with `train()` mode if the call sequence is `evaluate() → train() → evaluate()` and `evaluate()` forgot to set `.eval()`.

**Unverified**: I did not confirm whether `train_local` and `evaluate` explicitly set mode. **Action item for pass 2**: read both functions end-to-end.

**Fix proposal**: After `model.load_state_dict(...)` in `_load_model_from_message`, optionally call `model.eval()` and let each caller flip to train mode explicitly. Or: have the decorator do it.

**Bit-determinism risk**: **yes, possibly** — if the current code happens to depend on the previous mode, fixing it changes behavior. **Tag as bit-determinism risk and run paired-SLURM before/after.**

**Verification plan**: After fix, run paired 20-round runs and diff `summary.json`. If BN running stats are bit-identical, mode handling was already correct; if not, we found a real bug and should compare overall accuracy/ASR curves before declaring the fix net-positive.

### R-012 — Module-level caches (`_index_map_cache`, `_client_data_cache`, `_model_cache`) depend on `_make_cache_key` completeness. **LOW (likelihood) × HIGH (impact)**

**Location**: `fl_v2/src/fl_v2/client_app.py:47-50, 67-80`.

**Defect**: If a field that affects partitioning or data loading is added to `get_client_dataloaders` but the developer forgets to add it to `_make_cache_key`, two configs that should produce different data silently share a cached partition. The current key includes `data-root`, `num-clients`, `partition-mode`, `dirichlet-alpha`, `partition-seed`. Missing: `val-ratio`, `image-size`, `attack-type`, `label-flip-*`, `backdoor-*`. Several of those *change the loaded data* (attack params change the poison mask).

**Wait — the `_client_data_cache` is keyed on `client_id` alone, not on a config-aware key.** That means within a single Ray actor process, if the run config could ever change (which Flower doesn't currently allow, but might in the future), the cache returns stale data.

**Fix proposal**:
1. Extend `_make_cache_key` to include all fields that affect `get_client_dataloaders`'s output. Easier: cache-key the whole `frozen_run_config` excluding model-side fields.
2. `_client_data_cache` should key on `(client_id, cache_key)` not just `client_id`.

**Bit-determinism risk**: **no** in current usage (config doesn't change mid-process); risk surfaces only with future changes.

**Verification plan**: New test that creates a `ClientApp`, calls `_load_client_data` with config A, then config B (different `attack-type`), then asserts the returned `ClientDataLoaders` differ. Currently this would fail.

## Addendum — 2026-05-12 — "Double-launch" misdiagnosis (RETRACTED)

While reviewing the Pass-2 verification, I observed that every SLURM log
contains **two** `Starting Flower Simulation` and **two** `Successfully
installed flwr-gtsrb-v2` lines, plus exactly `2 × num-server-rounds`
"Round X — TRAIN" markers. I initially concluded that Flower 1.27.0
was launching every simulation twice — a race in the SuperExec polling
loop in `flwr.supercore.superexec.run_superexec.run_superexec` — and
authored a `BaseExecPlugin` venv patch to track launched `run_id`s.
Submitted and verified jobs:

- `6618560` / `6618561` — patched, but still showed 2 launches and ~8 min wallclock.
- `6618625` — same patch + a `print()` inside `launch_app` for instrumentation.

The instrumentation revealed:

- `[FL-V2 PATCH-DEBUG] launch_app called …` appears **once** per job.
- But `Starting Flower Simulation` still appears **twice**.
- `Successfully started run <run_id>` (CLI side, not subprocess) appears **once**.

That dichotomy is incompatible with "two subprocesses spawning". The
real explanation is in `flwr.common.logger.mirror_output_to_queue` at
line 344 of `common/logger.py`:

```python
def fn(s: str) -> int:
    ret = original_write(s)        # write to local stdout (→ SLURM .out)
    stream.flush()
    log_queue.put(s)               # also push to queue
    return ret
```

The simulation subprocess's stdout is intercepted: each line is written
to its **local** stdout (inherited to the SLURM `.out` file) AND pushed
to a log queue that gets uploaded to the SuperLink and **re-streamed**
back by `flwr run --stream`. The CLI's stdout also inherits to the
SLURM `.out` file. Net effect: every subprocess line appears **twice**
in the `.out`, but it is the same line being rendered twice, not two
real runs.

Cross-checks confirming a **single** run per `flwr run`:

- The debug print in `flower-superexec` (which does NOT call `mirror_output_to_queue`) appears once.
- `summary.json` contains exactly `num-server-rounds + 1` round entries (0..N), not `2N + 2`.
- The wandb run id appears once (no duplicate run created).
- Job wallclock fits "5 rounds × ~80 s + ~75 s startup ≈ 475 s", not "10 rounds × ~80 s ≈ 800 s".

**Wallclock per "YAML round" interpretation**: the speedup doc's
"60-62 s/round" target was measured on 20-round runs, where the ~75 s
one-time startup (dataset load + per-client histogram + Ray actor
warmup + initial-model build + wandb init) amortizes to ~3.75 s/round.
At 5 rounds the same startup is ~15 s/round, so the user-visible
"~95 s/YAML-round" on the Pass-2 verification jobs is the **correct**
number for a 5-round job — no actual double-launch.
